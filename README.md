# RYTM Backend

RYTM Backend is the Django REST API for a location-based events platform. It stores event information, supports geospatial filtering on a map, handles organizer submissions, and sends push notifications when events are approved.

## Project overview

This backend powers a mobile or web app that lets users discover nearby events such as restaurants, museums, parties, nature activities, and routes. Events are stored with geographic coordinates and are filtered by category and map bounds.

The project includes:

- Django + Django REST Framework API
- PostgreSQL/PostGIS database
- JWT authentication for organizers
- Event moderation workflow (`pending`, `approved`, `rejected`)
- Firebase Cloud Messaging push notifications
- Event photo uploads
- Map-based geographic filtering

## Tech stack

- Python 3.12
- Django 6.1.1
- Django REST Framework
- PostgreSQL + PostGIS
- JWT via `djangorestframework_simplejwt`
- Firebase Admin SDK
- Docker Compose for Postgres

### What each file/folder is for

#### `manage.py`
This is the main Django command-line entry point. It lets you run migrations, start the server, create a superuser, and execute tests.

#### `rytm/`
This is the Django project package. It contains the global project configuration.

- `rytm/settings.py` — project-wide settings such as database config, installed apps, middleware, authentication, and static files.
- `rytm/urls.py` — root URL routing. It includes the API app URLs and the JWT auth endpoints.
- `rytm/asgi.py` and `rytm/wsgi.py` — ASGI/WSGI entry points used by Django when serving the app in production or local development.

#### `events/`
This is the main application that handles the event platform logic.

- `models.py` — defines the database tables: `Organizer` and `Event`.
- `views.py` — API logic for listing and creating events.
- `serializers.py` — converts model data to JSON and validates incoming payloads.
- `urls.py` — defines the API routes for events and related endpoints.
- `signals.py` — reacts when an event is approved and sends a Firebase notification.
- `admin.py` — registers models in the Django admin dashboard.
- `tests.py` — test cases for the app.
- `migrations/` — database schema history generated by Django.

#### `docker-compose.yml`
Starts the Postgres + PostGIS database container locally. This avoids manually installing PostgreSQL on your machine.

#### `firebase-key.json`
Private Firebase credentials used to initialize Firebase Admin SDK. This is required for push notifications.

#### `requirements.txt`
Lists all Python dependencies needed for the backend.

#### `README.md`
Project documentation for developers: setup instructions, architecture, API behavior, and deployment notes.

## API endpoints

All API routes are mounted under `/api/`.

### Authentication

```http
POST /api/token/
POST /api/token/refresh/
```

These endpoints use JWT authentication.

### Events

```http
GET /api/events/
POST /api/events/
```

#### GET /api/events/
Returns approved events.

Optional query parameters:
- `category=<category_name>`
- `bbox=min_lon,min_lat,max_lon,max_lat`

Example:

```bash
curl "http://localhost:8000/api/events/?category=restaurants&bbox=24.0,49.8,24.1,49.9"
```

This filters events to a bounding box on the map.

#### POST /api/events/
Creates a new event request.

The backend automatically sets the created event status to `pending`.

## How the app works

This project is a backend for an event-discovery application. In simple terms, it works like this:

1. A client app or website sends a request to the API.
2. The API reads the event data from PostgreSQL/PostGIS.
3. Events are filtered by category or by map bounds before they are returned.
4. Organizers can submit new events through the API.
5. New events are saved with a `pending` status.
6. A moderator or admin approves the event in Django admin.
7. Once approved, the backend sends a push notification through Firebase.
8. Users receive the notification and can open the event in the mobile/web app.

### Request flow example

- A mobile app calls `GET /api/events/?category=party`
- Django receives the request in `events/views.py`
- `EventListCreateView` filters the queryset to only approved events
- The `EventSerializer` converts the database objects to JSON
- The API sends the response back to the app

### Organizer flow

- An organizer signs in using the JWT token endpoints
- The organizer sends `POST /api/events/`
- The API validates the payload with `EventSerializer`
- The event is created with `status='pending'`
- The event is not shown publicly until it is approved

### Moderation flow

The moderation model is built around statuses:

- `pending` — created but not approved yet
- `approved` — visible to users
- `rejected` — not accepted

This is useful because it prevents fake or low-quality events from appearing immediately on the map.

### Geospatial flow

The app stores each event location as a PostGIS `PointField`, which means it can answer map-related queries efficiently.

The `bbox` filter uses a bounding box like this:

```text
min_lon,min_lat,max_lon,max_lat
```

That lets the frontend ask: “Show me all events inside this map area.”

### Notification flow

When an event changes from not-approved to approved, a Django signal runs:

- `events/signals.py`
- `pre_save` on the `Event` model
- checks whether status changed to `approved`
- sends a Firebase topic message to `lviv_events`

This is meant for real-time updates in the client app.

## Local setup

### 1. Prerequisites

- Python 3.12+
- PostgreSQL with PostGIS
- Docker and Docker Compose
- `pip` and `virtualenv` or `venv`

### 2. Create a virtual environment

```bash
cd rytm-backend
python3 -m venv venv
source venv/bin/activate
```

### 3. Install dependencies

```bash
pip install -r requirements.txt
```

### 4. Start the PostGIS database

```bash
docker-compose up -d db
```

This creates a local PostgreSQL database named `rytm_db` with the user `rytm_user` and password `rytm_password`.

### 5. Configure environment variables

The project reads settings such as `SECRET_KEY` and `DEBUG` from environment variables.

Example:

```bash
export SECRET_KEY="your-secret-key"
export DEBUG="True"
```

If you want to use a database URL instead of the local Postgres settings, you can set:

```bash
export DATABASE_URL="postgis://rytm_user:rytm_password@127.0.0.1:5432/rytm_db"
```

### 6. Run migrations

```bash
python manage.py migrate
```

### 7. Start the development server

```bash
python manage.py runserver
```

The backend will be available at:

```text
http://127.0.0.1:8000/
```

## Firebase setup

The app initializes Firebase if `firebase-key.json` exists in the project root.

Create a Firebase service account key and save it as:

```text
firebase-key.json
```

This is used by the Firebase Admin SDK for sending push notifications when an event is approved.

## Push notifications

When an event status changes from anything else to `approved`, the signal in `events/signals.py` sends a Firebase topic notification to:

```text
lviv_events
```

This is designed for a mobile app that subscribes to that topic.

## Notes

- The project is currently a backend MVP for event discovery and moderation.
- The app is designed for map-based location filtering and event approval workflows.
- For production deployment, you should replace the default secret key and review security settings in `rytm/settings.py`.
